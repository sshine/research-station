# Kubernetes Operator

How to use Infisical to inject, push, and manage secrets within Kubernetes clusters

The Infisical Operator is a collection of Kubernetes controllers that streamline how secrets are managed between Infisical and your Kubernetes cluster. It provides multiple Custom Resource Definitions (CRDs) which enable you to:

* **Sync** secrets from Infisical into Kubernetes.
* **Push** new secrets from Kubernetes to Infisical.
* **Manage** dynamic secrets and automatically create time-bound leases.

When these CRDs are configured, the Infisical Operator will continuously monitor for changes and perform necessary updates to keep your Kubernetes secrets up to date. It can also automatically reload dependent Deployment resources whenever relevant secrets are updated. The short video below walks through how the Infisical Operator syncs secrets into your Kubernetes cluster.   
  

The operator supports two CRD API versions: **v1beta1** and **v1alpha1**. Use **v1beta1** for new installations; **v1alpha1** is legacy and will be deprecated soon.

If you’re already using the External Secrets operator, you can view the integration documentation for it [here](https://external-secrets.io/latest/provider/infisical/).

* Supported Kubernetes versions
* Supported Kubernetes distributions

The following [Kubernetes minor releases](https://kubernetes.io/releases/) are currently supported. The latest operator version is tested against each Kubernetes version. It may work with other versions of Kubernetes, but those aren’t officially supported.

* 1.33
* 1.32
* 1.31
* 1.30
* 1.29

The Infisical Kubernetes Operator has been tested successfully in the following hosted Kubernetes environments:

* Amazon Elastic Kubernetes Service (EKS)
* Google Kubernetes Engine (GKE)
* Microsoft Azure Kubernetes Service (AKS)
* Oracle Container Engine for Kubernetes (OKE)
* Red Hat OpenShift

It may work in other Kubernetes distributions, but those are not officially supported. Please report any issues [here](https://github.com/Infisical/infisical/issues).

## [​](#install) Install

The operator is installed via [Helm](/docs/self-hosting/helm-charts/secrets-operator).

1

Add the Helm repository

```
helm repo add infisical-helm-charts 'https://dl.cloudsmith.io/public/infisical/helm-charts/helm/charts/' helm  repo  add infisical-helm-charts 'https://dl.cloudsmith.io/public/infisical/helm-charts/helm/charts/' helm repo update helm  repo  update
```

2

Install the chart

The operator can be installed either cluster-wide or restricted to specific namespaces. If you require stronger isolation and stricter access controls, a namespace-scoped installation may make more sense.

* Cluster-wide (default)
* Namespace-scoped

The operator will watch and manage CRDs across all namespaces in the cluster. This is the default and quickest way to get started.

```
helm install --generate-name infisical-helm-charts/secrets-operator helm  install --generate-name infisical-helm-charts/secrets-operator
```

Limit the operator’s permissions to only specific namespaces instead of cluster-wide access. Useful for multi-tenant clusters or environments requiring strict resource isolation.

For multiple namespace-scoped installations, only the first installation should install CRDs. Subsequent installations should set `installCRDs: false` to avoid conflicts as CRDs are cluster-wide resources.

**Single namespace:**

```
helm install operator-namespaced infisical-helm-charts/secrets-operator \ helm  install operator-namespaced infisical-helm-charts/secrets-operator  \ --namespace single-namespace \ --namespace single-namespace  \ --set scopedNamespaces=single-namespace \ --set scopedNamespaces=single-namespace  \ --set scopedRBAC=true --set scopedRBAC= true
```

Using values.yaml file

values.yaml

```
 scopedNamespaces: single-namespace  scopedNamespaces: single-namespace scopedRBAC: true  scopedRBAC: true installCRDs: true  installCRDs: true
```

**Multiple namespaces (separate operators):**

```
helm install operator-1 infisical-helm-charts/secrets-operator \ helm  install operator-1 infisical-helm-charts/secrets-operator  \ --namespace ns1 \ --namespace  ns1  \ --set scopedNamespaces=ns1 \ --set scopedNamespaces=ns1  \ --set scopedRBAC=true \ --set scopedRBAC= true  \ --set installCRDs=true # Only install CRDs once in the cluster (default is true) --set installCRDs= true # Only install CRDs once in the cluster (default is true) helm install operator-namespace2 infisical-helm-charts/secrets-operator \ helm  install operator-namespace2 infisical-helm-charts/secrets-operator  \ --namespace ns2 \ --namespace  ns2  \ --set scopedNamespaces=ns2 \ --set scopedNamespaces=ns2  \ --set scopedRBAC=true \ --set scopedRBAC= true  \ --set installCRDs=false # Do not install CRDs in subsequent namespace installations --set installCRDs= false  # Do not install CRDs in subsequent namespace installations
```

Using values.yaml file

values-operator1.yaml

```

```

values-operator2.yaml

```
 scopedNamespaces: ns2  scopedNamespaces: ns2 scopedRBAC: true  scopedRBAC: true installCRDs: false  installCRDs: false
```

**Multiple namespaces (single operator):**

```
helm install operator infisical-helm-charts/secrets-operator \ helm  install  operator infisical-helm-charts/secrets-operator  \ --namespace operator-namespace \ --namespace operator-namespace  \ --set "scopedNamespaces={ns1,ns2,ns3}" \ --set "scopedNamespaces={ns1,ns2,ns3}"  \ --set scopedRBAC=true --set scopedRBAC= true
```

Using values.yaml file

values.yaml

```

```

3

Verify the deployment

Check the pods in the namespace you installed the operator into:

```
kubectl get pods --namespace <namespace> kubectl  get  pods --namespace < namespace>
```

If you installed cluster-wide without a `--namespace` flag, the operator is deployed into your current namespace (typically `default`), so run `kubectl get pods` without the flag.

### [​](#using-your-own-service-account) Using your own service account

By default a service account is created for the operator based on the release name. You can bring your own service account by setting `controllerManager.serviceAccount.create` to `false` and `controllerManager.serviceAccount.name` to the name of your existing service account.

values.yaml

```
controllerManager: controllerManager: serviceAccount:  serviceAccount: create: false  create: false name: my-service-account  name: my-service-account
```

The service account must already exist in the namespace you’re installing the operator in.

Custom service accounts are supported in chart version `0.10.11` and above.

## [​](#custom-resource-definitions) Custom resource definitions

* v1beta1 (Recommended)
* v1alpha1

The v1beta1 API separates authentication and connection configuration into their own reusable CRDs, making it easier to manage credentials across multiple secret resources.

| CRD | Description |
| --- | --- |
| [InfisicalConnection](/docs/integrations/platforms/kubernetes/infisical-connection-crd) | Defines how to connect to an Infisical instance (host, TLS). Referenced by other CRDs. |
| [InfisicalAuth](/docs/integrations/platforms/kubernetes/infisical-auth-crd) | Defines authentication credentials for a machine identity. Referenced by other CRDs. |
| [InfisicalStaticSecret](/docs/integrations/platforms/kubernetes/infisical-static-secret-crd) | Sync secrets from Infisical to a Kubernetes secret. Replaces `InfisicalSecret`. |

The v1alpha1 CRDs are legacy and are planned for deprecation.

| CRD | Status | Description |
| --- | --- | --- |
| [InfisicalSecret](/docs/integrations/platforms/kubernetes/infisical-secret-crd) | Deprecated | Sync secrets from Infisical to a Kubernetes secret. Use [InfisicalStaticSecret](/docs/integrations/platforms/kubernetes/infisical-static-secret-crd) (v1beta1) instead. See [migration guide](#migrating-from-v1alpha1-to-v1beta1). |
| [InfisicalPushSecret](/docs/integrations/platforms/kubernetes/infisical-push-secret-crd) | Active | Push secrets from a Kubernetes secret to Infisical. |
| [InfisicalDynamicSecret](/docs/integrations/platforms/kubernetes/infisical-dynamic-secret-crd) | Active | Sync dynamic secrets and create leases automatically in Kubernetes. |

## [​](#metrics-and-prometheus) Metrics and Prometheus

The operator exposes Prometheus metrics on `/metrics` for monitoring reconciliation performance, errors, and resource utilization.

### [​](#configuration) Configuration

Enable the ServiceMonitor during installation. This will create a prometheus `ServiceMonitor` resource in the same namespace as the operator.

values.yaml

```
telemetry: telemetry: serviceMonitor:  serviceMonitor: enabled: true  enabled: true # ... other telemetry configuration (optional) ... # ... other telemetry configuration (optional) ...
```

telemetry.serviceMonitor.enabled

Enable ServiceMonitor for Prometheus Operator. Defaults to `false`.

telemetry.serviceMonitor.selectors

Additional labels for ServiceMonitor. Defaults to `{}`.

telemetry.serviceMonitor.scheme

Scheme to use for the ServiceMonitor. Defaults to `https`.

telemetry.serviceMonitor.port

Port to use for the ServiceMonitor. Defaults to `https`.

telemetry.serviceMonitor.path

Path to use for the ServiceMonitor. Defaults to `/metrics`.

telemetry.serviceMonitor.interval

Scrape interval. Defaults to `30s`.

telemetry.serviceMonitor.scrapeTimeout

Scrape timeout. Defaults to `10s`.

telemetry.serviceMonitor.bearerTokenFile

Bearer token file. Defaults to `/var/run/secrets/kubernetes.io/serviceaccount/token`.

full-example-values.yaml

```
telemetry: telemetry: serviceMonitor:  serviceMonitor: enabled: true  enabled: true  selectors: {}  selectors: {} scheme: https  scheme: https port: https  port: https path: /metrics  path: /metrics bearerTokenFile: /var/run/secrets/kubernetes.io/serviceaccount/token  bearerTokenFile: /var/run/secrets/kubernetes.io/serviceaccount/token interval: 30s  interval: 30s scrapeTimeout: 10s  scrapeTimeout: 10s
```

## [​](#general-configuration) General configuration

### [​](#private/self-signed-certificate) Private/self-signed certificate

To connect to Infisical instances behind a private/self-signed certificate, you can configure TLS settings to point to a CA certificate stored in a Kubernetes secret resource.

* v1beta1 (Recommended)
* v1alpha1

In v1beta1, TLS is configured on the [InfisicalConnection](/docs/integrations/platforms/kubernetes/infisical-connection-crd) resource:

```
apiVersion: secrets.infisical.com/v1beta1 apiVersion: secrets.infisical.com/v1beta1kind: InfisicalConnection kind: InfisicalConnectionmetadata: metadata: name: my-infisical-connection  name: my-infisical-connectionspec: spec: address: https://infisical.mydomain.com  address: https://infisical.mydomain.com tls:  tls: caCertificate:  caCertificate: name: secret-containing-ca-certificate  name: secret-containing-ca-certificate namespace: default  namespace: default key: ca.crt  key: ca.crt
```

All CRDs that reference this `InfisicalConnection` will automatically use the configured TLS settings.

In v1alpha1, TLS is configured inline on each CRD:

```
spec: spec: hostAPI: https://app.infisical.com/api  hostAPI: https://app.infisical.com/api tls:  tls: caRef:  caRef: secretName: custom-ca-certificate  secretName: custom-ca-certificate secretNamespace: default  secretNamespace: default key: ca.crt  key: ca.crt
```

## [​](#templating) Templating

Fetching secrets from Infisical as-is via the operator may not be enough. This is where templating functionality may be helpful. Using Go templates, you can format, combine, and create new key-value pairs from secrets fetched from Infisical before storing them as Kubernetes Secrets or ConfigMaps. When a template is set, only the keys defined in `template.data` are included in the output. When no template is set, all fetched secrets are included as-is. Each secret is available in the template context as `.SECRET_KEY`, which is an object with two accessors:

* `.Value`: the secret value.
* `.SecretPath`: the path of the secret in Infisical.

### [​](#key/value-template-map) Key/value template map

```
targets: targets: - name: my-app-config - name: my-app-config namespace: default  namespace: default kind: Secret  kind: Secret creationPolicy: Owner  creationPolicy: Owner template:  template: engineVersion: v1  engineVersion: v1 data:  data: DSN: "{{ .SECRET.Value }}.namespace:{{ .SECRET2.Value }}"  DSN: "{{ .SECRET.Value }}.namespace:{{ .SECRET2.Value }}" ANOTHER_ONE: "{{ .SECRET3.Value }}"  ANOTHER_ONE: "{{ .SECRET3.Value }}"
```

### [​](#bulk-string-template-with-a-loop) Bulk string template with a loop

```
targets: targets: - name: all-secrets - name: all-secrets namespace: default  namespace: default kind: Secret  kind: Secret creationPolicy: Owner  creationPolicy: Owner template:  template: engineVersion: v1  engineVersion: v1 data: |  data: | {{- range $key, $secret := . }} {{- range $key, $secret := . }} {{ $key }}: "{{ $secret.Value }}" {{ $key }}: "{{ $secret.Value }}" {{- end }} {{- end }}
```

To help transform your secrets further, the operator provides a set of built-in functions that you can use in your templates.

### [​](#available-helper-functions) Available helper functions

The Infisical Secrets Operator exposes a wide range of helper functions to make it easier to work with secrets in Kubernetes.

encodeBase64

Encodes a string to a base64-encoded string (e.g. `hello world` becomes `aGVsbG8gd29ybGQ=`).**Signature**

```
encodeBase64(plainString string) string encodeBase64(plainString  string) string
```

**Template usage**

```
template: template: data:  data: ENCODED_SECRET: "{{ .MY_SECRET.Value | encodeBase64 }}"  ENCODED_SECRET: "{{ .MY_SECRET.Value | encodeBase64 }}"
```

decodeBase64ToBytes

Decodes a base64-encoded string back to its original value (e.g. `aGVsbG8gd29ybGQ=` becomes `hello world`).**Signature**

```
decodeBase64ToBytes(encodedString string) string decodeBase64ToBytes(encodedString  string) string
```

**Template usage**

```
template: template: data:  data: DECODED_SECRET: "{{ .MY_BASE64_SECRET.Value | decodeBase64ToBytes }}"  DECODED_SECRET: "{{ .MY_BASE64_SECRET.Value | decodeBase64ToBytes }}"
```

pkcs12key

Extracts all private keys from a PKCS#12 archive and returns them as PKCS#8 PEM-encoded blocks (`-----BEGIN PRIVATE KEY-----...`). The archive must not be password-protected — use `pkcs12keyPass` for password-protected archives.**Signature**

```
pkcs12key(input string) string pkcs12key(input  string) string
```

**Template usage**

```
template: template: data:  data: tls.key: "{{ .TLS_CERT_PKCS12.Value | pkcs12key }}" tls.key: "{{ .TLS_CERT_PKCS12.Value | pkcs12key }}"
```

pkcs12keyPass

Same as `pkcs12key`, but uses the provided password to decrypt the PKCS#12 archive.**Signature**

```
pkcs12keyPass(password string, input string) string pkcs12keyPass(password  string, input  string) string
```

**Template usage**

```
template: template: data:  data: tls.key: '{{ pkcs12keyPass "my-password" .TLS_CERT_PKCS12.Value }}' tls.key: '{{ pkcs12keyPass "my-password" .TLS_CERT_PKCS12.Value }}'
```

pkcs12cert

Extracts all certificates from a PKCS#12 archive and returns them as an ordered PEM chain (`-----BEGIN CERTIFICATE-----...`). Sort order: **leaf → intermediate(s) → root**. If disjunct or multiple leaf certs are provided, they are returned as-is. The archive must not be password-protected — use `pkcs12certPass` for password-protected archives.**Signature**

```
pkcs12cert(input string) string pkcs12cert(input  string) string
```

**Template usage**

```
template: template: data:  data: tls.crt: "{{ .TLS_CERT_PKCS12.Value | pkcs12cert }}" tls.crt: "{{ .TLS_CERT_PKCS12.Value | pkcs12cert }}"
```

pkcs12certPass

Same as `pkcs12cert`, but uses the provided password to decrypt the PKCS#12 archive.**Signature**

```
pkcs12certPass(password string, input string) string pkcs12certPass(password  string, input  string) string
```

**Template usage**

```
template: template: data:  data: tls.crt: '{{ pkcs12certPass "my-password" .TLS_CERT_PKCS12.Value }}' tls.crt: '{{ pkcs12certPass "my-password" .TLS_CERT_PKCS12.Value }}'
```

pemToPkcs12

Takes a PEM-encoded certificate and private key and creates a base64-encoded PKCS#12 archive. The output is not password-protected — use `pemToPkcs12Pass` to set a password.**Signature**

```
pemToPkcs12(cert string, key string) string pemToPkcs12(cert  string, key  string) string
```

**Template usage**

```
template: template: data:  data: keystore.p12: '{{ pemToPkcs12 .TLS_CERT.Value .TLS_KEY.Value }}' keystore.p12: '{{ pemToPkcs12 .TLS_CERT.Value .TLS_KEY.Value }}'
```

pemToPkcs12Pass

Same as `pemToPkcs12`, but encrypts the PKCS#12 archive with the provided password.**Signature**

```
pemToPkcs12Pass(cert string, key string, password string) string pemToPkcs12Pass(cert  string, key  string, password  string) string
```

**Template usage**

```
template: template: data:  data: keystore.p12: '{{ pemToPkcs12Pass .TLS_CERT.Value .TLS_KEY.Value "my-password" }}' keystore.p12: '{{ pemToPkcs12Pass .TLS_CERT.Value .TLS_KEY.Value "my-password" }}'
```

fullPemToPkcs12

Takes a full PEM-encoded certificate chain (leaf + intermediates + root) and a private key, and creates a base64-encoded PKCS#12 archive that includes the entire chain. The output is not password-protected — use `fullPemToPkcs12Pass` to set a password.**Signature**

```
fullPemToPkcs12(cert string, key string) string fullPemToPkcs12(cert  string, key  string) string
```

**Template usage**

```

```

fullPemToPkcs12Pass

Same as `fullPemToPkcs12`, but encrypts the PKCS#12 archive with the provided password.**Signature**

```
fullPemToPkcs12Pass(cert string, key string, password string) string fullPemToPkcs12Pass(cert  string, key  string, password  string) string
```

**Template usage**

```
template: template: data:  data: keystore.p12: '{{ fullPemToPkcs12Pass .TLS_FULL_CHAIN.Value .TLS_KEY.Value "my-password" }}' keystore.p12: '{{ fullPemToPkcs12Pass .TLS_FULL_CHAIN.Value .TLS_KEY.Value "my-password" }}'
```

filterPEM

Filters PEM blocks by type from a bundle containing multiple PEM blocks (e.g. extract only `CERTIFICATE` or `PRIVATE KEY` blocks). Common PEM types: `CERTIFICATE`, `PRIVATE KEY`, `PUBLIC KEY`, `RSA PRIVATE KEY`.**Signature**

```
filterPEM(pemType string, input string) string filterPEM(pemType  string, input  string) string
```

**Template usage**

```
template: template: data:  data: ca.crt: '{{ filterPEM "CERTIFICATE" .TLS_BUNDLE.Value }}' ca.crt: '{{ filterPEM "CERTIFICATE" .TLS_BUNDLE.Value }}' tls.key: '{{ filterPEM "PRIVATE KEY" .TLS_BUNDLE.Value }}' tls.key: '{{ filterPEM "PRIVATE KEY" .TLS_BUNDLE.Value }}'
```

filterCertChain

Filters PEM certificates by their position in a certificate chain. The chain is automatically ordered before filtering. Accepted types: `leaf` (end-entity certificate), `intermediate` (all intermediate CA certificates), `root` (root CA certificate). Returns an empty string if the requested type is not present in the chain.**Signature**

```
filterCertChain(certType string, input string) string filterCertChain(certType  string, input  string) string
```

**Template usage**

```
template: template: data:  data: tls.crt: '{{ filterCertChain "leaf" .TLS_CHAIN.Value }}' tls.crt: '{{ filterCertChain "leaf" .TLS_CHAIN.Value }}' ca.crt: '{{ filterCertChain "root" .TLS_CHAIN.Value }}' ca.crt: '{{ filterCertChain "root" .TLS_CHAIN.Value }}' intermediate.crt: '{{ filterCertChain "intermediate" .TLS_CHAIN.Value }}' intermediate.crt: '{{ filterCertChain "intermediate" .TLS_CHAIN.Value }}'
```

Takes a JSON-serialized JWK and returns a PEM block of type `PRIVATE KEY` containing the private key. Uses [`x509.MarshalPKCS8PrivateKey`](https://pkg.go.dev/crypto/x509#MarshalPKCS8PrivateKey) internally.**Signature**

toYaml

Marshals a value to a YAML string. Returns an empty string on marshal error.**Signature**

```
toYaml(v any) string toYaml(v  any) string
```

**Template usage**

```
template: template: data:  data: config.yaml: "{{ .APP_CONFIG.Value | fromYaml | toYaml }}" config.yaml: "{{ .APP_CONFIG.Value | fromYaml | toYaml }}"
```

fromYaml

Parses a YAML string into a `map[string]any`, useful for extracting individual fields from a YAML-formatted secret (e.g. `(fromYaml .DB_CONFIG.Value).host` returns the `host` field).**Signature**

```
fromYaml(str string) map[string]any fromYaml(str  string) map[string] any
```

**Template usage**

```

secretFrom

This function is only available in `v1beta1` resources (e.g. `InfisicalStaticSecret`).

Resolves a secret from a specific folder path within the Infisical project. Takes a path and a secret name as parameters, and returns the secret’s value by default. You can optionally use `.Value` or `.SecretPath` accessors on the result — if omitted, `.Value` is used.This is especially useful when multiple secrets share the same key, either from recursive fetches across different paths or from multiple sources. In both cases, the merge strategy only keeps the first occurrence (read more [here](/docs/integrations/platforms/kubernetes/infisical-static-secret-crd#sources)), so `secretFrom` lets you explicitly select the one you need by its full path.

If multiple sources contain a secret with the same name and path, the secret from the first source listed in the `sources` array will be used.

**Signature**

```
secretFrom(path string, secretName string) string secretFrom(path  string, secretName  string) string
```

**Template usage**

```

## [​](#migrating-from-v1alpha1-to-v1beta1) Migrating from v1alpha1 to v1beta1

This migration guide applies to `InfisicalSecret` only. `InfisicalPushSecret` and `InfisicalDynamicSecret` don’t have v1beta1 replacements yet and should continue to be used as-is.

The v1beta1 API introduces a cleaner separation of concerns. Instead of defining authentication and connection details inline in each secret CRD, you now create dedicated `InfisicalConnection` and `InfisicalAuth` resources that can be shared across multiple secret resources.

### [​](#key-changes) Key changes

* **Secret resource:** `InfisicalSecret` -> `InfisicalStaticSecret` `InfisicalStaticSecret` replaces the v1alpha1 `InfisicalSecret` CRD. Instead of defining auth and connection settings inline, it references dedicated `InfisicalAuth` and `InfisicalConnection` resources.
* **Authentication:** inline `authentication` -> `InfisicalAuth` Authentication config is now defined in a standalone `InfisicalAuth` resource that can be reused across CRDs. Authenticated credentials are cached and shared by all resources referencing the same `InfisicalAuth`.
* **Connection:** inline `hostAPI` / `tls` -> `InfisicalConnection` Connection config is now defined in a standalone `InfisicalConnection` resource that can be reused by auth and secret resources.

### [​](#migration-steps) Migration steps

1

Create an InfisicalConnection resource

Extract the `hostAPI` and `tls` settings from your existing CRD into a new `InfisicalConnection` resource. See the [InfisicalConnection CRD](/docs/integrations/platforms/kubernetes/infisical-connection-crd) documentation for the full spec.

2

Create an InfisicalAuth resource

Extract the `authentication` block from your existing CRD into a new `InfisicalAuth` resource. See the [InfisicalAuth CRD](/docs/integrations/platforms/kubernetes/infisical-auth-crd) documentation for the full spec.

3

Replace InfisicalSecret with InfisicalStaticSecret

Create a new `InfisicalStaticSecret` resource that references your `InfisicalConnection` and `InfisicalAuth` resources. See the [InfisicalStaticSecret CRD](/docs/integrations/platforms/kubernetes/infisical-static-secret-crd) documentation for the full spec.If you were using templates, note that `engineVersion` is now a required field and the only accepted value is `v1`. The `includeAllSecrets` option no longer exists. Instead, you can iterate over all secrets using a bulk string template with a range loop. See the [Templating](#templating) section for details and examples.

4

Delete the old v1alpha1 resource

Once you have verified that the new v1beta1 resources are working, delete the old `InfisicalSecret` CRD instance.
